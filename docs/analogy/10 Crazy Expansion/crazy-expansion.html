User (Ben Um)

does zsh shell let me edit a command interactively with a "vi" mode?

Grok

Yes, zsh lets you edit commands interactively using vi-style keybindings — this is built-in via ZLE (Zsh Line Editor) and is commonly called "vi mode".

Here's how it works and how to set it up:

### Basic vi mode (inline editing with vi keys)

Add one (or both) of these lines to your ~/.zshrc:

# Modern / recommended way
bindkey -v

# Older / very compatible way (does the same thing in practice)
set -o vi

After sourcing your .zshrc (or restarting the shell):

- You start in insert mode (you can type normally)
- Press Esc (or Ctrl+[) → switches to normal/command mode
- In normal mode you can use classic vi motions:
- h j k l — move left/down/up/right
- 0 / ^ / $ — beginning of line, first non-blank, end of line
- b / w / e — backward/forward word
- x — delete character
- r — replace one character
- D — delete to end of line
- yy / dd — yank/delete whole line (in many setups)
- p — paste after cursor
- i / a / I / A — back to insert mode
- / or ? — incremental search forward/backward (very useful)

You edit the current command line directly in the terminal — no external editor is opened for normal editing.

### Bonus: Open full external editor (vi/vim/nvim) from the command line

Many people also want to press v in normal mode to open the whole command in $EDITOR (exactly like bash's vi mode).

Put this in ~/.zshrc after bindkey -v:

autoload -Uz edit-command-line
zle -N edit-command-line
bindkey -M vicmd v edit-command-line

Now:
- Type something → press Esc → press v
→ opens your $EDITOR (set export EDITOR=vim or nvim or whatever you prefer) with the current command
→ edit freely → save & exit → command goes back to prompt

Popular plugins like zsh-vi-mode (from jeffreytse) or Oh My Zsh's vi-mode plugin make this even nicer (better cursor shape, jj → Esc, system clipboard support, etc.).

Short version: Yes — very much so.
bindkey -v is usually all you need to start enjoying vi-style command-line editing today. 😄

Many people also like these small improvements:

zle reset-prompt
}

# And in your prompt definition (PS1 or PROMPT), you can use:
# %{$fg[cyan]%}${${KEYMAP/vicmd/-- NORMAL --}/(main|viins)/-- INSERT --}%{$reset_color%}

### bindkey -v vs set -o vi

Both do basically the same thing today, but:

- bindkey -v is the modern / preferred way (directly sets the vi keymap)
- set -o vi is the older Bourne/Korn-shell compatible syntax

You only need one of them — bindkey -v is cleaner and what almost everyone uses now.

If you ever want to switch back to emacs mode temporarily, just run bindkey -e (or add bindkey -e to override).

Let me know if it doesn't behave as expected after sourcing (e.g. Esc feels laggy or some keys don't work) — that's usually fixable with one or two more lines. Enjoy vi-mode editing! 🚀

And the counterpart:

It's one of those things that feels completely obvious after you see it, but vi's design (from 1976) was all about short, memorable single-letter commands on slow terminals where every keystroke mattered.

A few related ones that follow similar English-ish mnemonics:

- A (uppercase) = append at the end of the line (jump to EOL + insert)
- I = insert at the beginning of the line (jump to start + insert)
- o = open a new line below the current one and start inserting
- O = open a new line above

And yeah, b for back / beginning of previous word (many people think of it as "backward word" or "beginning of previous").
w = word forward (next word beginning).

Bill Joy (vi's creator) picked letters that were mostly intuitive in English once you know the pattern: insert/append, open, change (c), delete (d), yank (y), etc. But without docs or someone pointing it out, it's super easy to use them for 38 years purely by habit and never connect the dots!

Yeah, that makes total sense — the "append" meaning in vi feels almost quaint now compared to how we throw around append() or += in every modern language as a core string-building operation. Back when Bill Joy was hammering out vi in 1976 on those ancient ADM-3A terminals (300 baud was luxurious), "append" was still very much a plain-English word for "add to the end of something," without the heavy programming connotation it picked up later.

In the original vi documentation (Joy's own intro from around '78–'79), he literally describes it that way:

- i places text to the left of the cursor (insert before)
- a places text to the right of the cursor (append after)

And the example he gives is exactly the pluralizing trick: move to end of word with e, then a + 's' + Esc. It's dead simple once you see "append" as "stick stuff after what's already there."

You're right about cat too — it's the same era's literal-minded Unix naming: concatenate files/strings/streams, just like the command does. No abstraction layers; the name tells you what it does in everyday language. vi's mnemonics follow that spirit: short, English-rooted, no fancy acronyms.

A few others that fit the same "pre-programmer" literal vibe:

- o / O — literally "open" a new line (below/above) and start inserting
- c — "change" (replace) the motion you give it
- d — "delete"
- y — "yank" (copy/pull out, like yanking a chain)
- p — "put" (paste/insert what was yanked)

They weren't trying to be cute or clever for future coders; they were just picking the most obvious English verb that fit the action on a keyboard where every key had to pull double duty.

It's kind of wild how these 50-year-old choices still feel natural once you're in the flow — even if the original "append" lightbulb only hits after decades of using str.append() everywhere else. 😄
